# Analytics event dictionary

The machine-readable source of truth is `ANALYTICS_EVENTS` in [`src/lib/analytics/events.ts`](../src/lib/analytics/events.ts). This page explains it for people. When the two disagree, the code wins; update this page in the same PR as the taxonomy.

Destination today: PostHog project **Zuey.me** (env setup: [env-setup.vi.md §14](env-setup.vi.md#14-analytics-posthog)). GA4 is planned as a second destination behind the same adapter interfaces (`src/lib/analytics/destinations/types.ts`).

## Rules for every event

- **Declared only.** An event must exist in `ANALYTICS_EVENTS` with the matching source (`client` events through `track()`, `server` events through `captureServerEvent()`/`sendServerEvent()`). Unknown events, undeclared properties, missing required properties and wrong types are dropped, never sent partially.
- **Property kinds.** `string`, `number`, `boolean`, `url`. `url` values are stripped of sensitive query/fragment parameters before sending. Any string longer than 500 characters is rejected (free text such as chat content does not fit an analytics property).
- **No personal data.** A string that contains an email address, a JWT or a secret token (`zm_`, `zoa_`, `zor_`, `zk_`, `sk_`, `whsec_`, GitHub/Slack token prefixes) rejects the whole event when it is a `string` property; in a `url` property those values are replaced by `[redacted]` instead.
- **Envelope.** Every event gets `event_version` (the event's `version`) and `schema_version` (`ANALYTICS_SCHEMA_VERSION`). Bump `version` when a property changes meaning; add a new event instead of changing the trigger.
- **Never break business logic.** `track()`, `identify()`, `reset()` never throw. Server capture never rejects; it returns `{ delivered, uuid, results[], rejected? }` with a per-destination outcome (`disabled`, `invalid`, `timeout`, `network`, `http`). Default server timeout 2.5 s.

## Never collected

Email, name, avatar, phone number; passwords, sign-in links, tokens, API keys, OAuth codes; Zuey AI chat text, questions and prompts; bank account numbers, card details, transfer memos; booking and survey form input. The privacy page (`/privacy#analytics`) states the same list to visitors.

## Automatic PostHog data

PostHog still records `$pageview`, `$pageleave` and autocapture clicks, plus `$web_vitals` (LCP, CLS, INP, FCP; `capture_performance: { web_vitals: true, network_timing: false }`) and `$exception` for unhandled errors and promise rejections (`capture_exceptions`); console errors and network timing are not captured. Both options are set in `PERFORMANCE_CAPTURE_OPTIONS` and posthog-js loads their extensions lazily, so they add no bundle weight and follow the same consent gate. Before anything leaves the browser, `before_send` (`scrubCaptureResult`) deep-scrubs `properties`, `$set` and `$set_once`:

- URLs (`$current_url`, `$referrer`, `$initial_*`, `href` attributes) lose these parameters (case-insensitive): `token`, `code`, `email`, `key`, `secret`, `sig`, `signature`, `state`, `session`, `password`, `pass`, `pwd`, `auth`, `otp`, `api_key`, `apikey`, `access_token`, `refresh_token`, `id_token`, `client_secret`, `confirm_email`, `new_email`, `jwt`, `hmac`, `nonce`, `ticket`, `manage` (booking manage token), `payerid` (PayPal), plus any name containing `token`, `secret`, `password`, `email`, `session` or `signature`. URL user-info is removed.
- zuey.me's own URLs (root-relative, `zuey.me`, `www.zuey.me`) also lose the free-text search parameter `q` (the only one the site's pages read, `/articles?q=…`), so search words never reach `$current_url`, `$session_entry_url`, `$referrer`, `$initial_*`, autocapture `href`s or the `knowledge_search` event's URL. Other sites' URLs keep their `q`. Inside free text (`$elements_chain`, error messages), where the host is unknown, a `q=` value is replaced by `[redacted]`.
- URLs of private pages (`/account`, `/login`, `/billing`, `/booking`, `/chat`, `/connect`, `/oauth`, `/studio`, `/courses/orders`) lose the whole query string and fragment, e.g. the PayPal booking return `/booking/{id}?manage=…&paypal=return&token=…&PayerID=…`.
- Order codes and booking ids in paths become placeholders everywhere (`/billing/:code`, `/billing/card/:id`, `/courses/orders/:code`, `/booking/:id`), in `$current_url`, `$pathname`, `$referrer`, `$initial_*` and any other string: the order code is the SePay transfer memo. On those pages the `title` property is blanked.
- Every other string has emails, JWTs, secret tokens and inline `name=value` pairs of those parameters replaced with `[redacted]`. Emails with Unicode (IDN) domains such as `user@bücher.example` are matched too. Retina asset names (`image@2x.png`, `logo@3x.webp`: `@`, one or two digits, `x`, an image extension and no further labels) are file names and are kept; `a@2x.example.com` is still an email. Emails are also found in their percent-encoded forms (`%40`, double-encoded `%2540`, any hex case, `+` or `%20` around them): each URL segment is decoded as UTF-8 until it stops changing, up to 8 passes (a segment still encoded after that is redacted whole), malformed `%` sequences are left as they are, and the segment is re-encoded with the email replaced (encoded non-ASCII text and `mailto:` keep their form), so `$referrer`, `$session_entry_referrer`, `$current_url`, `$pathname` and `$initial_*` never carry a decoded email.
- The scrubber inspects at most 16 KB per string (`MAX_SCRUB_LENGTH`). A longer value is cut at the last URL delimiter before that point and ends in `[redacted]`, so a half-cut email or token is never kept. Every pattern runs in linear time, so a crafted long link cannot stall `before_send`.
- `$exception` messages are free text that can echo what the visitor typed. After scrubbing, `$exception_message` and each `$exception_list[].value` are cut to 200 characters (`MAX_EXCEPTION_TEXT_LENGTH`, then `…`). On private pages (the list above, so `/chat` and `/studio` too) and while the Zuey AI panel is mounted on any page (`enterSensitiveSurface()`), they are replaced by `[redacted]`; only the error type and the scrubbed stack frames (file, line, column, function) are kept (`hardenExceptionProperties`).
- If scrubbing fails, the event is dropped.

Autocapture is off on `/account`, `/login`, `/billing`, `/booking`, `/chat`, `/connect`, `/oauth`, `/studio` and `/courses/orders`, and these components carry `ph-no-capture` wherever they are embedded: the Zuey AI panel, survey blocks (vote labels are private), the booking widget, the course checkout form, the company-invoice fields and the `/connect` Telegram link island (its link token never reaches the page; it stays in an HttpOnly cookie). Session replay is disabled in code (`disable_session_recording: true`); enabling it later needs a masking review for auth, billing, AI and booking screens first. Feature flags are disabled too (`advanced_disable_flags: true`): posthog-js builds the `/flags` request's `person_properties` from raw `$set` and `$initial_*` values that never pass through `before_send`. The same option skips PostHog remote config (`/array/{token}/config`), so settings made in the PostHog UI are ignored: heatmaps, web vitals, surveys, exception autocapture, dead clicks and the server-side autocapture opt-out. The site uses none of them; enable any of them in `postHogInitOptions` instead. Without remote config, autocapture sends elements as the `$elements` array of objects (`attr__href`, `$el_text`, ...) rather than the `$elements_chain` string; `scrubValue` scrubs both shapes.

## Environments and consent

- Key and host come from `PUBLIC_POSTHOG_KEY` / `PUBLIC_POSTHOG_HOST` (runtime binding first, currently the `[vars]` of `wrangler.toml`, then build-time env). The built-in key of project Zuey.me is used only by production builds without a configured key.
- The browser captures only on `zuey.me` and `www.zuey.me` in production builds. Preview deployments (`*.pages.dev`) are production builds and receive the same key from `wrangler.toml`, but their hostname is not allowlisted, so they stay silent; so do `localhost` and dev builds. `PUBLIC_ANALYTICS_DEBUG=1` lifts the hostname/dev check.
- The server sends nothing outside production builds, and only when the request host is `zuey.me` or `www.zuey.me` (`isServerCaptureHost()` in `src/lib/analytics/server.ts`, the same allowlist as the browser). A preview deployment (`*.pages.dev`) therefore never delivers server events to the production project: its outbox drain answers `skipped` with `skipped_reason: "not_production_host"` and leaves the rows queued. `PUBLIC_ANALYTICS_DEBUG=1` lifts both checks.
- PostHog is not even initialised (no network request) when the browser sends Do Not Track (`1`/`yes`) or Global Privacy Control, when the visitor turned analytics off at `/privacy#analytics` (localStorage `zuey_analytics_opt_out=1`), or when the browser blocks localStorage. Blocked storage (reading or writing throws; probed once per page with the temporary key `zuey_analytics_storage_probe`) gives the consent state `storage_blocked`: `/privacy#analytics` then says storage is blocked and shows no toggle, because no choice could be saved. Opting out also calls PostHog `opt_out_capturing()` and `reset()`.
- These browser choices do not cover [server events](#server-events). Account and purchase events (sign-up, sign-in, purchases, refunds, payment issues, subscription lifecycle) are recorded from payment and sign-in webhooks on the server, not from the browser, so they are sent regardless of the toggle, Do Not Track or GPC. They use only the pseudonymous member id (never an email, phone number or token), carry `$geoip_disable: true` so no location is derived from the server's IP, and booking guests' events carry `$process_person_profile: false` so no person profile is created for them. The privacy page (`/privacy#analytics`) says the same.

## Identity lifecycle

| Situation | What happens |
|---|---|
| Anonymous visitor | PostHog anonymous id; `person_profiles: 'identified_only'`, so no person profile is created |
| Page load with a verified member session | `bootAnalytics()` asks `/api/members/auth/identity` and calls `identify(member_id)`. The answer is cached in the tab (sessionStorage) for 10 minutes, or 2 minutes when signed out; the cache is used only while it matches the browser-wide identity key (localStorage), and it is removed, never written, on `/login`, `/account`, `/oauth`, so the page after a sign-in redirect identifies at once |
| Already identified | `identify()` is skipped only when PostHog's `get_distinct_id()` already equals the member id |
| Member signs out (`/account`, Studio member session) or deletes the account | `reset()` before navigating: clears the stored member and starts a new anonymous id. Sign-out on `/account` first sends `logout` under the member id (`signOutAnalytics()`); the admin Studio does not run analytics, so its sign-out only resets. Account deletion only resets |
| Session expired or ended on another device | The next identity check returns `null` and the browser is reset |
| A different member signs in on the same browser | `reset()` first, then `identify()`; the two people are never merged |
| Sign-out in another tab | That tab's `reset()` clears the shared identity key; other tabs ignore their now-stale cache and re-check the server |

Known limit: if the previous member's session ended without this browser running `reset()` (expired, signed out on another device, cookies cleared by hand), the first `$pageview` of the next visit is still attributed to that member, because PostHog sends it before the identity check answers. The browser is reset right after, so later events are not.

Only the opaque member id (`users.id`) is ever used as `distinct_id`. `identify()` refuses anything that is not an id-shaped string (`[A-Za-z0-9_.:-]{1,200}`, no email/JWT/secret). No person properties (`$set`) are sent with identify.

**AI metrics.** `latency_ms` (from accepting the question to the end of the reply) and `cost_cents` (the estimated cost counted against the plan's AI budget) are measured by the server and sent in the chat SSE `done` frame next to `usage`; the `error` frame carries `latency_ms`. The browser only copies those numbers, so it never measures or sends message content. A route-level failure before the run starts has no latency.

**Known limits.** `community_joined` is observed by the browser, not by the Telegram webhook: the card re-checks memberships when the member returns to the tab (focus or visibility change) after requesting an invite, so a join on another device, or after the page was closed, is not counted. `article_engaged` needs both thresholds and counts only visible seconds. The engagement events never carry the search text, and neither does the `/articles?q=…` page address: `before_send` drops `q` from every zuey.me URL property (see Automatic PostHog data).

**Late hydration.** React islands can hydrate before the layout's boot script decides consent. `track()` calls made before that are queued (at most 50, `MAX_PENDING_EVENTS`) and sent once analytics activates, or dropped when it stays off (DNT, GPC, opt-out, blocked storage, non-production host). Mount-time events use `trackOnce(key, …)`, which sends a key once per page load, so React StrictMode double effects and remounts do not double count.

**Session attribution.** On the first page of a tab session where analytics is active, `src/lib/analytics/attribution.ts` stores (sessionStorage `zuey_analytics_attribution`, wrapped in try/catch) the first touch: the five `utm_source`, `utm_medium`, `utm_campaign`, `utm_term`, `utm_content` values that are slug-like campaign codes (`utm_source=google`, `utm_campaign=spring-2026`): after trimming and lowercasing, only `a-z`, `0-9`, `.`, `_`, `-`, at most 64 characters, no run of 8 or more digits and no token. Anything else (spaces, so names and search terms; `@`, `+`, `%`; phone numbers) drops that value entirely; free text is never kept. The referrer is kept as its **origin only** (http/https, other sites only; `zuey.me` and `www.zuey.me` count as the same site). Paths and queries are dropped because they routinely carry search terms, webmail message ids, document ids and sign-in tokens; the origin is enough to tell channels apart. Click ids (`gclid`, `fbclid`) and any other parameter are ignored. Later pages in the session keep the first touch, a direct visit stays direct, and the stored value is re-validated on read. Every client event of the session then carries `session_utm_*` and `session_referrer` when present. Opting out removes the stored value; nothing is stored while analytics is off.

**Funnel join.** `pricing_viewed` → `plan_selected` → `begin_checkout` → `purchase` (server) → `subscription_activated` (server) share one `distinct_id` for a member: the browser identifies with `member_id` from `/api/members/auth/identity`, which is `users.id`, the same id the server outbox uses (covered by a test in `tests/analytics-outbox.test.ts`). Creating an order requires a signed-in member (an anonymous `begin_checkout` is followed by a redirect to sign in), so `checkout_created` and `payment_initiated` are always identified; steps taken anonymously before sign-in in the same browser are merged into the member by PostHog at `identify()`. Not joined, by design:

- Booking guests: the server events use a one-off `guest_` id (hash of the booking id, no person profile), so a guest's `booking_*` client steps and their `purchase` stay separate. Join on aggregate counts, not on people.
- Browsers with analytics off: the server `purchase` and subscription events still arrive (see Environments and consent) with no client steps before them.

### Server events

Owner `revenue` covers payments and subscriptions. Server events are written to the analytics outbox right after the verified state change, as a separate statement, and delivered later (see below). `distinct_id` is the member id (`users.id`); a booking guest has no account and gets `guest_` + 24 hex characters of SHA-256 of the booking id, sent with `$process_person_profile: false`. Every server event is sent with `$lib: "zuey-me-server"` and `$geoip_disable: true`. Amounts are what the customer paid (tax included), in major units of the original currency, never converted: VND as paid, USD cents / 100. A refund carries the amount the provider reports taken back, with `partial` when it is less than the payment.

## Server event outbox

Table `analytics_outbox` (`migrations/0022_analytics_outbox.sql`), code in `src/lib/analytics/outbox.ts` and `src/lib/analytics/commerce-events.ts`.

- **One row per fact, at-least-once delivery with idempotent keys.** Each row has a `dedupe_key` with a unique index; a repeat insert is ignored. Keys come from the verified fact, not from the webhook delivery: `purchase:<provider>:<transaction>` where the transaction is the billing/course order id for one-time orders (one order is paid once; extra transfers are flagged instead), the Dodo payment id (each renewal charge has its own id) or the PayPal capture / SePay transaction id for bookings. An admin resolve of a flagged booking reuses the key of the first transaction recorded for it and sums what the guest paid in the booking's currency across providers; without a recorded transaction it uses `booking:<booking id>` and the price due. A resolve queues nothing when the booking was already confirmed with recorded money before (it is cancelled or flagged and its `attention_reason` was empty or `admin`: a payment that flags a booking always sets its own reason; a held or expired booking was never counted), so a webhook-counted booking that is flagged or cancelled and resolved again is not counted twice, whatever the outbox still holds. Lifecycle keys include the resulting `period_end`, so a renewal or a later re-activation is a new event, and the drain's expiry sweep uses the same key as the recompute.
- **Payment first.** The insert is a separate statement after the payment state has been written and every error is caught and logged (`analytics outbox: could not queue …`); a failed or missing outbox never changes a webhook's answer or a member's access.
- **Delivery.** The `zuey-me-scheduler` Worker calls `POST /api/v1/analytics/outbox/drain` every 5 minutes with `CRON_SECRET` (admins may call it too; optional body `{ "limit": 1–40 }`, default 30). The drain first queues `subscription_expired` for prepaid periods that ended in the last 3 days (one `INSERT … SELECT`, at most 200 per run), then leases due rows in batches of 10 (2-minute lease, a crashed run's rows are reclaimed), sends each through `sendServerEvent()` with the row id as event `uuid` so PostHog de-duplicates a retried delivery, and writes each batch's outcome with one `UPDATE` per group of rows that share it. It stops after 20 seconds.
- **Bounded runs.** One run issues at most 20 D1 statements (`MAX_DRAIN_QUERIES`) and 40 PostHog requests, under the Workers free plan's 50 per invocation. A batch is claimed only when its worst case (one claim plus one settle statement per row) still fits; a typical run of 30 deliveries uses about 9 statements. The response reports `queries`, `pending` (rows still waiting) and `budget_exhausted`.
- **Retry.** A failed row is retried after 5, 10, 20, … minutes (capped at 6 hours), so it survives a destination outage of about 22 hours. A row is marked `dead` with `last_error` and never retried automatically after 10 attempts, on a payload rejection (HTTP 400/413/422), or when the taxonomy no longer accepts its payload. Auth errors (401/403/404) from a wrong or rotated key are retried. After fixing the cause, an operator requeues dead rows with `UPDATE analytics_outbox SET status = 'pending', attempts = 0, next_attempt_at = <now ISO> WHERE status = 'dead'` (record a time-travel restore point first).
- **Monitoring.** The scheduler reads each drain summary (`workers/scheduler/src/analytics-drain-check.ts`). It logs a warning when rows were dead-lettered while others were delivered, when fewer than three claimed rows were all retried (a transient timeout), or when the run was skipped on a non-production host. It fails the cron invocation when nothing was delivered and either at least three claimed rows all failed or a row was dead-lettered, or when analytics is disabled on the production host while rows are pending.
- **Retention.** Delivered rows are deleted 30 days after `sent_at` (up to 500 per run, index `(status, sent_at)`); pending and dead rows are kept. Dedupe keys are not needed after that window: providers redeliver webhooks within days, lifecycle keys include the period end, the expiry sweep looks back only 3 days, a dispute won later restores access without queueing a purchase, and a booking re-resolved after money was recorded for it queues nothing (see above). One case still relies on the key: a booking resolved without any recorded transaction, then flagged or cancelled and resolved again more than 30 days after delivery, is counted a second time.
- **Preview gate.** Without a destination (not a production build, no key, or a non-production host) the drain claims nothing and the rows stay `pending`.
- **Dodo refunds of renewals.** Refund and dispute webhooks carry only the payment id. Every collected Dodo charge is recorded in `payment_events` as `charge:<payment id>` with its card, so a refund or lost dispute of a renewal charge is matched to its card, logged (`billing.card_reversal` with `renewal: true`) and queues one `refund` keyed by the refund/dispute id. Only a first-payment reversal reverses the referral commission. A payment with no `charge:` row (a refund or dispute that beats its `payment.succeeded`, or a renewal charged before charge rows existed) is looked up with Dodo `GET /payments/{id}`; dispute webhooks name no customer, so the lookup's `subscription_id` is what ties it to a card, or, while no card webhook has stored that subscription id yet, the `card_ref` in the payment's checkout metadata (only for a card not bound to another subscription, and only when the metadata's `user_id` and `plan` are the card's, as for `payment.succeeded`). A renewal of a card that already has a first payment is matched at once. On a card with no first payment yet, the webhook answers `409 payment_not_recorded` so Dodo redelivers it after the charge (Dodo makes 8 attempts over about 28 hours: 0, 5 s, 5 min, 30 min, 2 h, 5 h, 10 h, 10 h). A lookup Dodo rejects (a 4xx other than 408 or 429, such as an unknown payment), a lookup that cannot run (no `DODO_API_KEY`) or a payment of no card here is acknowledged as `ignored`. A lookup that fails on a network error, a Dodo 408, 429 or 5xx, or the 10-second timeout every Dodo API call has answers `502 payment_provider_error` before anything is written, so Dodo redelivers the reversal. The `refund` event is queued before the activity log, and the log write throws on failure, so a retry after a partial failure logs the reversal once.
- **Dodo charge count.** Promo coverage and the minimum accepted charge depend on which charge of the card this is. It is the number of distinct `charge:<payment id>` rows, so a payment redelivered under a new webhook id counts once, plus one per `payment.succeeded` webhook row received more than a minute before the card's first charge row (charges collected before charge rows existed, whose payment id was never stored).

## Realtime presence

Live visitor counts for the Activity Monitor. **Not a PostHog event** and never written to D1. Per-visitor state (category, last heartbeat, opaque key) exists only on the open WebSocket inside the `zuey-me-presence` Worker's Durable Object (`workers/presence`) and expires `PRESENCE_TTL_MS` (75 s) after the last heartbeat; it is gone when the socket closes. That Durable Object's own storage keeps only the owner's public status with its change time and a signature of the last published aggregate, nothing per visitor. The shared contract is [`src/lib/presence/contract.ts`](../src/lib/presence/contract.ts).

- **Consent.** The beacon (`src/lib/presence/presence-beacon.ts`, started lazily from `src/layouts/Layout.astro` via `presence-beacon-boot.ts`) connects only while `canTrack()` is true: the same Do Not Track, Global Privacy Control, local opt-out and blocked-storage rules as PostHog above. It re-checks consent every 5 s, on `storage` events from other tabs and on the `zuey:consent-change` event the `/privacy#analytics` toggle dispatches, and closes the socket at once on opt-out. Like browser analytics it runs only on `zuey.me` / `www.zuey.me` unless `PUBLIC_ANALYTICS_DEBUG=1`.
- **Ticket.** `POST /api/v1/presence/ticket` (`src/lib/presence/presence-ticket-issuer.ts`) signs a 2-minute ticket with `PRESENCE_TICKET_SECRET`. The server alone decides `m` (member session cookie, same origin only; API keys ignored) and `o` (member id listed in `PRESENCE_OWNER_MEMBER_IDS`, never the admin role). The dedupe key `k` is an HMAC truncated to 32 characters of `m:<member id>` (one member across tabs and devices), `b:<browser id>` for counted guests, or a random nonce for watch-only tickets (`count: false`, never counted). Rate limit: about 120 tickets per 10 minutes per client IP (IPv6 counted per /64), held in isolate memory (per edge isolate, reset on eviction; the Worker's per-IP connection caps, also per /64 for IPv6, are the backstop). The ticket is sent as the second WebSocket subprotocol (`new WebSocket(url, ['zuey-presence.v1', ticket])`), never in the URL, so request logs never record it; the Worker answers with `zuey-presence.v1` and logs neither the ticket nor `k`. The beacon caches its counting ticket in sessionStorage `zuey_presence_ticket` (per tab) and reuses it across page loads and reconnects until 15 s before it expires, only for guest tickets (never member or owner ones, so a sign-out cannot reuse them), only for the same browser id and while consent is granted; opting out deletes it. A tab opened in the background connects only once it is shown.
- **Browser id.** localStorage `zuey_presence_id`, 24 random base64url characters, created only when consent is granted, so all tabs of one browser count once. It never leaves the browser except in the ticket request, and the server only keeps its HMAC.
- **What is sent.** Over the WebSocket only `{ "t": "hb", "cat": <category> }` and `{ "t": "idle" }`: no URL, title, query, id or free text. `cat` is one of `reading`, `zueytube`, `reads`, `ai`, `courses`, `exploring`, `other` from `categoryFor()` in `src/lib/presence/presence-category.ts` (route prefix, or the focused ZueyOS window on `/`, reported by the `zuey:app-focus` event). Heartbeat on connect and every 25 s while the tab is visible and the visitor active; after 120 s without pointer, key, scroll or touch input, or when the tab is hidden, one `idle`; at most one message per 5 s per socket. `pagehide` closes the socket, and so does a tab hidden for 60 s (it reconnects when shown). Reconnects use exponential backoff with jitter (capped at 60 s) and stop for the page after repeated `401`/`503` ticket answers or 5 sockets in a row that never opened (Worker down or upgrade refused; each drops the cached ticket).
- **Activity Monitor feed.** Asks for a watch-only ticket first; the ticket answer's `url` names the Worker (runtime `PUBLIC_PRESENCE_URL`), from which it reads `GET /v1/snapshot` and opens the socket. If the ticket endpoint fails (`503`, `429`, network), it polls `GET /v1/snapshot` about every 20 s from the last known origin (else the build-time `PUBLIC_PRESENCE_URL` or the default) and retries the ticket with backoff up to 5 minutes; it shows lost connection or unavailable only when the snapshot itself cannot be read. "Updated … ago" for an HTTP snapshot counts from the snapshot's own `at`, so a cached or fallback snapshot shows its real age. The presence Worker keeps console logs but disables invocation logs, which would record the ticket-carrying `Sec-WebSocket-Protocol` header. The hub pushes on every change plus a keepalive at least every 45 s to subscribers, so a quiet but healthy feed is not shown as stale. `GET /v1/snapshot` is served from a 2 s per-isolate memo and a 5 s edge cache in front of the single Durable Object; if the hub fails, the last snapshot is served for at most 5 minutes, then `503`.
- **Owner status.** The owner is a member id listed in `PRESENCE_OWNER_MEMBER_IDS`, never the admin role. Only the owner reads or sets it, through `GET`/`PUT /api/v1/presence/owner`, MCP `presence_status_get` / `presence_status_set` or the Studio **Presence** tab (`src/lib/presence/presence-owner-identity.ts`; other admins get `403 not_owner`, never see the tools and see only the diagnostics section of the tab; scoped keys and OAuth tokens need `account:read` / `account:write`). Owner keys and OAuth tokens reuse the `account:read` / `account:write` scopes. Pages forwards the setting to the Worker's private `/internal/owner` only over the `PRESENCE` service binding (top-level in `wrangler.toml`, so every Pages environment; HTTP to an `https:` or loopback origin only when no binding exists, redirects never followed), authenticated by a time-bound `X-Presence-Internal` value `<unix seconds>.<HMAC>` valid for ±120 s (`src/lib/presence/internal-auth.ts`, `presence-owner-client.ts`). Modes: `auto` (online while the owner has a live counted connection, so the owner's own browser must allow counting; else offline), `away`, `busy`, `offline` and `invisible`; `invisible` is published exactly like `offline` (status `offline`, `onSite: false`, no text), so nothing public tells them apart. Optional status text is plain (line breaks and tabs become spaces, other control characters and bidi override/isolate marks are dropped, then trimmed), at most 80 UTF-16 units, shown only while the public status is not offline, and kept only in the Worker's Durable Object storage.
- **What is published.** Aggregates only (`PresenceSnapshot`): active visitors (owner excluded), signed-in members among them, and a category breakdown. Groups smaller than `PRESENCE_MIN_GROUP` (3) are folded into `other`, `members` is `null` below 3 and the breakdown is empty while fewer than 3 visitors are active, so no one is singled out.

- **24h history.** `GET {origin}/v1/history` on the Worker (`PresenceHistory`, same CORS rules as `/v1/snapshot`, edge-cached for a minute) returns 288 five-minute buckets, oldest first. Each bucket keeps the peak unique `active` count and the category counts at the moment of that peak; nothing per visitor, no members count and no owner data. The same suppression as the snapshot applies to every bucket when it is published: a bucket whose peak is below `PRESENCE_MIN_GROUP` (3) has an empty breakdown, and inside a bucket groups smaller than 3 are folded into `other`. Raw counts stay in the Durable Object's own storage (one key, written when the current bucket's peak rises, at most one write per rise and none while nobody is live; see [presence-operations.md](presence-operations.md#cost-model)) and are dropped after 24 h. Slots with no recording read back as peak 0, and the Activity Monitor draws them as 0, not as gaps. The Activity Monitor reads history from the same Worker origin as the snapshot, only while its window is open and the page visible, about every 5 minutes (`src/lib/presence/presence-history.ts`); times are shown in the viewer's local time zone, and a failed load shows "history unavailable" without touching the live numbers.
- **Admin diagnostics.** `GET /api/v1/presence/diagnostics` (any admin or read-only Studio key; Studio **Presence** tab) proxies the Worker's private `/internal/diagnostics`: socket counts, limits, counters, alarm timing and history storage size. Counts and timings only, never keys, IPs, tickets or owner text; the Pages client re-builds the answer from the contract's fields. Operations: [presence-operations.md](presence-operations.md).

## Adding an event

1. Add the entry to `ANALYTICS_EVENTS` (name in `snake_case`, `version: 1`, `source`, `owner`, `trigger`, `props`).
2. Call `track('name', { ... })` in the browser or `captureServerEvent(env, 'name', memberId, { ... })` on the server; TypeScript enforces the property shape.
3. Add a row to the table above and a test case if the event has non-trivial properties.
4. Server events that must not be lost go through `enqueueServerEvent()` with a dedupe key derived from the verified fact (see the outbox section); never call `captureServerEvent()` for them.

## Verifying in production

PostHog → *Activity → Live events*, filtered to project Zuey.me:

1. `$pageview` from zuey.me shows a `$current_url` without sensitive parameters (try `/login/verify?token=test`).
2. After signing in and reloading, events carry the member id as `distinct_id`; after signing out, a new anonymous id.
3. With Do Not Track/GPC on, or after "Turn analytics off" on `/privacy#analytics`, no new events arrive from that browser. Server-side account and purchase events still arrive under the member id (see Environments and consent).
