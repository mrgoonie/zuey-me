<p>Một bài có nhiều nhãn có kiểu riêng, quản lý được qua editor, API và MCP. <strong>Fact không đồng nghĩa với đúng mãi mãi:</strong> một khẳng định có nguồn có thể đã outdated ở phiên bản hoặc thời điểm khác. Bài pha trộn nhiều loại nội dung có nhãn tới block/claim cụ thể.</p>

<details>
<summary>Cấu trúc nhãn &amp; cách truy vấn</summary>
<p>ID nhãn ổn định, type/facet, tên hiển thị EN/VI/ZH/KO/JA và aliases. Schema kiểm tra label ID/type/version, không tự tạo nhãn lạ từ input hoặc aliases mơ hồ; nhãn chưa biết được đề xuất riêng để admin duyệt taxonomy. Hỗ trợ thêm/sửa/merge nhãn có kiểm soát; giữ ánh xạ ID cũ. Taxonomy ID dùng chung giữa các locale; nhãn chủ đề có thể gắn ở cấp article, nhãn kiểm chứng/độ cập nhật gắn theo locale/claim khi cần; evidence, scope claim và độ cập nhật có thể khác từng bản dịch/revision. Không tự suy ra mọi bản dịch đều đã kiểm chứng.</p>
<p>Record gắn nhãn: article/locale/revision + label ID + scope article/block/claim + nguồn bằng chứng + as_of + reviewed_at + review_due_at + tool/model version áp dụng + người/phương thức đề xuất + admin duyệt + lý do. Một URL tự nó chưa đủ: auditor phải truy xuất nguồn, đối chiếu claim với trích đoạn/bằng chứng, thời điểm và phiên bản áp dụng; ghi ngày lấy nguồn và lý do kết luận. Nguồn mất, mâu thuẫn hoặc không kiểm tra được thì trả needs-review/câu hỏi cho admin; không tự xác nhận fact. AI confidence chỉ là độ tự tin đề xuất, không phải bằng chứng đúng. Không gắn fact cho toàn bài nếu chỉ một phần đã xác minh.</p>
<p>API/MCP search kết hợp facet, nhiều nhãn (AND/OR rõ), freshness, locale và as_of. Trả label metadata, phạm vi/nguồn/ngày kiểm tra và lý do outdated. Retrieval hiển thị cảnh báo nguồn outdated; khi hỏi hiện trạng ưu tiên nguồn đã kiểm tra phù hợp thời điểm/phiên bản, khi hỏi lịch sử vẫn tìm được nguồn cũ. Jev/ranking không biến nhãn thành bảo đảm chính xác.</p>
</details>

<h3>Chia sẻ bài &amp; Markdown cho AI tools</h3>
<p>Toolbar trong trang đọc: share bài, copy as Markdown, mở bản Markdown only, copy Markdown URL và send to ChatGPT/Claude/Gemini. URL canonical theo locale; route song song <code>/vi/knowledges/slug.md</code> và tương tự EN/ZH/KO/JA khi bản đó đã publish.</p>
<p>
<code>.md</code> trả <code>Content-Type: text/markdown; charset=utf-8</code>, chỉ văn bản Markdown, không HTML giao diện hoặc JavaScript thực thi. Serialize cùng revision và blocks được cấp quyền: headings, lists, tables, code fences, link/caption cho media/embed; interactive block có mô tả và link để mở tương tác.</p>

<p>REST và CLI gửi <code>Authorization: Bearer $ZUEY_API_KEY</code>; lưu key qua secret store/biến môi trường, không đối số command dễ lọt vào history. MCP remote dùng OAuth đã đề xuất; client hỗ trợ header trực tiếp có thể dùng key cùng scope tại <code>/mcp</code>. Không đặt key trong URL hoặc chuyển tiếp key Zuey đến provider. OAuth grants có màn hình quản lý/thu hồi riêng.</p>
<p>Key thuộc user ID bất biến; server cấp secret ngẫu nhiên bằng crypto, chỉ lưu hash + fingerprint, owner, scopes, expires_at, revoked_at và last_used_at. Chỉ session đã đăng nhập của chủ tài khoản (CSRF protection, xác minh lại khi cần) được list/tạo/rotate/thu hồi. API key thường không được cấp thêm key. List không trả lại secret; revoke/hết hạn có hiệu lực trên REST, CLI, MCP và cache.</p>
<p>Rotate tạo replacement với cùng hoặc hẹp hơn scopes; key cũ chỉ được thu hồi khi user xác nhận đã đổi ở công cụ. Ghi audit metadata, không ghi secret/nội dung riêng; session ownership, quota và membership hiện tại luôn được kiểm tra. Hết hạn/hạ gói không bị bỏ qua bởi credential cũ.</p>
</details>
<details class="developer-details">
<summary>Contract API / MCP đề xuất</summary>
<p>Session-only: <code>GET/POST /api/v1/account/api-keys</code>, <code>POST /api/v1/account/api-keys/:id/rotate</code>, <code>DELETE /api/v1/account/api-keys/:id</code>. Tạo/rotate trả secret đúng một lần với <code>Cache-Control: no-store</code>; list chỉ metadata. Validate scope allowlist, expiry và owner, idempotency cho create/rotate, 404 cho key không thuộc user, 409 cho revision conflict. MCP user chỉ xem metadata key và thu hồi own key với scope/xác nhận riêng; không mint/reveal secret qua tool response hoặc chat transcript. Quản lý key chính ở /account.</p>
</details>
</section>
<details class="info">
<summary>Contract cho trang /account thực tế</summary>
<p>SSR bảo vệ bằng session; API và MCP cùng user ID. Profile, avatar R2 (kiểm tra MIME thật, giới hạn size, re-encode/remove metadata), lịch sử, payment portal và chat chỉ được truy cập bởi chủ tài khoản; admin đọc chats theo policy, scope và audit. Thay email phải xác minh lại; thay ảnh hoặc tên không cấp thêm quyền.</p>
<p>User xem/xuất/xoá session, quản lý memory riêng và gói/hoá đơn; xoá chat không huỷ giao dịch bắt buộc lưu. URL không chứa token hay nội dung cá nhân; trả dữ liệu private với cache phù hợp. Verify user A không thể đọc/sửa data user B qua browser, REST hoặc MCP.</p>
</details>

<p>KHÔNG sử dụng dữ liệu cá nhân cho mục đích khác. Email và trạng thái gói phục vụ đăng nhập, thanh toán và cấp quyền. Nội dung chat phục vụ trả lời, giữ lịch sử, bộ nhớ bạn bật, hỗ trợ và bảo vệ dịch vụ. Telegram ID chỉ dùng liên kết tài khoản và quản lý nhóm theo gói.</p>

<p>Không bán/cho thuê dữ liệu, không dùng cho quảng cáo nhắm mục tiêu, profiling thương mại hoặc huấn luyện/fine-tune AI. Chat không được đưa vào analytics nội dung, session replay hoặc kho kiến thức công khai. Không gửi lịch sử riêng trong URL share/send-to-AI.</p>

<h3>04 / Ai có thể đọc hội thoại?</h3>
<p>Hội thoại và bộ nhớ được tách riêng từng user. Người dùng khác không được truy cập. Admin Zuey có thể thống kê, tìm và xem tất cả chat sessions còn lưu để vận hành, hỗ trợ và xử lý sự cố dịch vụ; chỉ tài khoản admin đã xác minh và scope phù hợp được phép.
