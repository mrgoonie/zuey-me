## 2. #180: thêm `admin` vào `scopes_supported`

Base của PR là 911ffda (trước #181). Merge với origin/main tự động, không conflict (`tests/oauth-mcp.test.ts` auto-merge).

### Còn cần không / #181 thay thế bao nhiêu?
- **Phần code vẫn cần, #181 không làm**: #181 chỉ thêm `_meta["me.zuey/toolCatalogVersion"]` và test chứng minh admin thấy tool media. Nó không đổi metadata. Trên main, `src/lib/oauth/metadata.ts` vẫn quảng bá chỉ scope member, nên connector xin "đúng scope được quảng bá" sẽ không bao giờ xin `admin`. Đây là nguyên nhân gốc của #173 mà #180 sửa (`metadata.ts:39`).
- UI consent (`src/pages/oauth/authorize.astro:115`): `admin` không bao giờ tick sẵn, kể cả khi client xin. Hợp lý vì client nay sẽ xin `admin` cho mọi người.
- Docs `docs/env-setup.vi.md`: hướng dẫn reconnect ở `/account` và tick `admin`, cache `tools/list` 5 phút. Khớp `TOOLS_LIST_TTL_MS` và `ConnectedApps` trên `/account`.

### Test trùng với #181 / main (`tests/oauth-mcp.test.ts` trên nhánh #180)
- `:712` "registers every media tool…": trùng test #181 ở `:608` (#181 còn chặt hơn, so tập `media_*` chính xác).
- `:720` "hides media tools…": phần ẩn tool trùng `:608`; challenge step-up `scope="admin"` đã có ở `:580`.
- `:738` "lists media tools for an admin grant and an admin API key…": trùng `:608`.
- `:765` "keeps list results private…": `cacheScope`/`ttlMs` đã test ở `:676-678`.
- **Duy nhất có giá trị mới**: `:749` "lets an admin who explicitly ticks admin…": assert `scopes_supported` có `admin`, admin bỏ tick thì không có tool media, non-admin xin đủ scope quảng bá vẫn không có `admin`.
- Đề xuất: giữ `:749`, bỏ 4 test còn lại (không push, vì task không cho phép sửa #180).

### An toàn: non-admin có lấy được `admin` không? Không.
- Consent: `buildView` (`src/lib/oauth/authorize.ts:173-174`) lọc `admin` khỏi `offered` nếu `!isAdminIdentity(...)`; `decideConsent` chỉ nhận scope nằm trong `offered`, nên POST giả `scope=admin` cũng bị bỏ.
- Code/token: scope của code là scope đã chọn ở consent; refresh chỉ được thu hẹp (`tokens.ts:163` `invalid_scope` nếu vượt grant).
- Mỗi request: `caller.ts:65` `admin = adminIdentity && token.scopes.includes('admin')`. Nếu email bị gỡ khỏi `ADMIN_EMAILS` thì mất quyền ngay dù token còn `admin`.
- Kết luận: thay đổi chỉ là quảng bá, không nới quyền.

### Rủi ro thật: bug refresh-token #183 (nêu trong comment epic #170)
Comment của mrgoonie trên #170 (2026-10-17) nhắc "a related refresh-token bug, tracked in #183". Issue #183 (OPEN, P1) chưa có PR. Đã xác minh trên main: `refreshTokens` (`src/lib/oauth/tokens.ts:151`) ghi `rotated_at` **trước** khi kiểm `invalid_scope` (`:163`), `checkResourceParam` và `consentActive` (`:170`). Một refresh bị từ chối vẫn làm cháy refresh token; client thử lại token cũ thì cả family bị revoke và người dùng phải đăng nhập lại.

#180 làm bug này dễ xảy ra hơn: client gửi lại danh sách scope đã quảng bá (giờ có `admin`) khi refresh sẽ bị `invalid_scope` với **mọi member không phải admin**, và cả admin đã bỏ tick `admin` (UI mới mặc định bỏ tick). Hậu quả: phải đăng nhập lại mỗi khi access token hết hạn.
- **#183 thuộc phạm vi rollout của #180** (là điều kiện để deploy an toàn), nhưng theo AGENTS.md nên làm PR riêng, không gộp vào #180. Đề xuất: merge fix #183 trước hoặc cùng đợt với #180. Fix tối thiểu: kiểm scope/resource/consent trước khi claim rotation, hoặc giao (intersect) scope yêu cầu với scope đã grant, kèm test "widen bị từ chối thì refresh token vẫn dùng được".
