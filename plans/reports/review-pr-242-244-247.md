## #242: search words in PostHog URLs

### Bypass probe (merged tree, `scrubUrl` / `scrubValue` / `scrubCaptureResult`)

**Dropped or redacted** (correct):

- `?q=`, `?Q=`, `?%71=` (`URLSearchParams` decodes the name), repeated `q`, and `#q=`.
- `www.zuey.me`, `ZUEY.ME` (the URL parser lowercases the host), `:8443`, `http:`, and relative `/articles?q=` and `/articles/page/2?q=`.
- Protocol-relative `//zuey.me/...?q=` and a scheme-less `zuey.me/articles?q=`: both go through `redactString`, and the value becomes `[redacted]`.
- These properties in a full capture: `$current_url`, `$referrer`, `$initial_person_info.u`, `$set_once.$initial_current_url`, `$elements[].attr__href` and `$elements_chain`.
- The `knowledge_search` event's `$current_url`, which comes out as `https://zuey.me/articles?lang=vi`.
- Exception frame filenames, and free text such as `error at https://zuey.me/articles?q=jane%20doe`.

**Kept:**

- `?q[]=`, `?q%5B%5D=`, `;q=` and `#/x?q=`. The site never produces these, and `/articles` reads only `searchParams.get('q')`, so they are attacker-made links, not words the visitor typed.
- Another site's `?q=`, such as Google, or the ChatGPT/Claude/Gemini share links in `ArticleActionBar`. Their text is a prompt about an article, not a visitor search.

**Other readers checked:**

- I checked every `searchParams.get` and `URLSearchParams` reader under `src/pages` and `src/components`. `q` is the only free-text search parameter, read through `parseDiscoveryQuery` for `/articles` and `/articles/page/N`.
- `KnowledgesPanel` on the home page and `ReadsBrowser` keep their query in React state, not in the URL. Only the panel's "browse all" `href` carries it, and that `href` is scrubbed.
- The `/articles` `<title>` does not include `q`.
- The `<input name="q" value=…>` is not captured, because posthog-js `isSensitiveElement` drops the attributes of text inputs.
- `next=` builders point to `/login` (a private path, so the whole query is dropped) or to the server-side `/r/{code}` redirect.

### Findings

- **nit**, `src/lib/analytics/pii.ts:71` and `pii.ts:330`. In free text, `INLINE_PARAM_RE` only matches literal names (`[A-Za-z0-9_.-]+`), so `$elements_chain` `attr__href="/articles?%71=jane"` keeps the value. `scrubUrl` handles the same input. The site never emits an encoded `q` name, so only a crafted link is affected. Fix if wanted: allow `%XX` in the name and decode it before the check.
- **nit**, `pii.ts:306`. `ownSite` uses only `PRODUCTION_HOSTNAMES`:
  - A trailing-dot host (`https://zuey.me./articles?q=jane`) keeps `q`.
  - A preview host with analytics debug on keeps `q`.
  - Neither is real production traffic. `parsed.hostname.replace(/\.$/, '')` would close the first case.
- **nit**, `pii.ts:330`. In free text, the redaction also hits other sites' `q`: `$elements_chain` `attr__href="https://www.google.com/search?q=zuey"` becomes `q=[redacted]`. The docs say this ("inside free text ... a `q=` value is replaced"). It costs a little data quality and does not leak anything.
- **Info (not this PR), nested own URLs.** An own URL encoded inside another parameter, such as `https://zuey.me/x?next=%2Farticles%3Fq%3Djane`, keeps its inner `q`. No site-generated link on a non-private page does this.

### The three changed assertions: legitimate

- `tests/analytics.test.ts:41`. The "keeps search keywords" test encoded the old contract. It now expects `q` to be dropped and still checks that `keyword` and `utm_campaign` are kept.
- `tests/analytics-encoded-pii.test.ts:71-72`. "URLs without emails are unchanged" now uses `topic=` on zuey.me. It still checks that `100%25%20free%2Bcourse` and encoded Vietnamese text round-trip unchanged, and the Google `?q=` URL still covers `q` on another host.

No other existing assertion changed in any of the three PRs.

## #244: retina asset names

`RETINA_ASSET_RE` (`/^@\dx\.(?:png|jpe?g|gif|webp|avif|svg)$/i`, `pii.ts:31`) is tested against the whole greedy domain match (`pii.ts:128`).

### Probe results

**Still redacted** (`redactString`; `containsPii` returns true):

- `a@2x.example.com`, `x@2x.png.evil.com`, `jane@2x.png.co` and `jane@2X.PNG.evil.com`.
- `jane%402x.png.evil.com`, `jane%402x.png%2Eevil.com` and `jane@2x.png%2Eevil.com`. The literal pass skips them, then the encoded pass decodes the segment and catches the full domain.
- `jane@2x.pngx`, `jane@22x.png`, `jane@2x.jpg-evil.com`, `jane@2x.svg.vn` and `Jane <jane@2x.webp.example.org>`.
- `a@2x.png b@3x.jpg c@example.com`: only the email is redacted.
- `jane@2x.png@example.com` becomes `jane@[redacted]`.

**Kept:**

- `image@2x.png`, `logo@3x.webp`, `/assets/icon@2x.svg?v=1`, `icon%402x.svg` and `icon%25402x.svg`.
- `jane@2x.png.`, `jane@2x.png/evil.com` and `jane@2x.png<ZWSP>.evil.com`. None of these is a usable address, because `png`, `jpg`, `jpeg`, `gif`, `webp`, `avif` and `svg` are not TLDs.

**No bypass found.** A real email can never have a domain that is exactly `<digit>x.<image extension>`.

### Findings

- **nit**, `pii.ts:31`. Only one digit is allowed, so `@10x.png` is still redacted. That is a false positive only and cannot leak anything.

## #247: exception text

### What I checked

**The private-path check uses the raw URL.**

- `pii.ts:195` reads the raw `$current_url`, and falls back to `$pathname`.
- `/chat?x=1`, `/chat/abc`, `/studio#articles`, and a `$pathname`-only `/studio` all drop the message text.
- Every entry of a cause chain is redacted.

**Message lengths.**

- A long message on `/` becomes 201 code units (200 plus `…`).
- The emoji (surrogate-pair) edge case is handled.

**Which fields carry message text.**

- Current posthog-js (`PostHog/posthog-js` main) builds `$exception` from `$exception_list` (`type`, `value`, `mechanism`, `stacktrace`) and `$exception_level` (`error-properties-builder.ts`).
- `$exception_steps` holds only breadcrumbs from `addExceptionStep`, which the site never calls, plus PostHog's own "dropped" messages.
- `$exception_values` and `$exception_types` are used only locally for suppression rules.
- So `$exception_list[].value`, plus the older `$exception_message`, are the only fields that carry the message, and the PR covers both.
- Any other string still goes through `scrubValue`. For example, a legacy `$exception_stack_trace_raw` is scrubbed but not blanked.

**The counter is one shared instance.**

- In the merged build, the hardening code is in exactly one chunk, `dist/_astro/client.*.js`.
- That chunk is imported by both `Layout.astro`'s boot script (which sets `before_send`) and the two `ZueyAiPanel` chunks.
- So `enterSensitiveSurface` and `before_send` share one `openSensitiveSurfaces` counter. React StrictMode's double effect leaves it at 1, and cleanup is idempotent.

**The wider private-path list is accepted, as instructed.**

- Nothing breaks: the event type, mechanism and frames are kept.
- `/CHAT` and `/vi/chat` are not matched, but neither is a real route.

**`/privacy`** is unchanged by #247. It still says "error type, message and code location, filtered as above", which stays true now that less is sent.

**Performance.** A 16 KB message costs 0.04 ms through `scrubCaptureResult`.

### Findings

- **nit**, `src/lib/analytics/destinations/posthog.ts:126-138` and `src/components/ai/ZueyAiPanel.tsx:323`. The counter tracks whether the panel is mounted, not whether it is visible.
  - Once the home ZueyOS AI window hydrates (`client:visible`) or the article drawer is opened (it stays mounted, just `hidden`), every later exception on that page load loses its message text, even after the window or drawer is closed.
  - The docs correctly say "mounted". This is stricter privacy at some cost to debugging, which is acceptable.
- **nit**, `posthog.ts:124`. `/privacy` could mention the 200-character cap. This is optional; the current wording is not wrong.

## Performance (16 KB adversarial strings, median of 5, via `scrubValue`)

| Input | bun main | bun merged | node/V8 main | node/V8 merged |
| --- | --- | --- | --- | --- |
| `aaaa@2x.png` repeated | 0.39 ms | 0.45 ms | 0.42 ms | 0.70 ms |
| `a@2x.png%40` repeated | 0.37 ms | 1.08 ms | 0.30 ms | 1.11 ms |
| `@2x.png` repeated / `a@2x.png@2x.png…` chain | 0.38 / 0.31 ms | 0.38 / 0.38 ms | 0.50 / 0.53 ms | 0.41 / 0.41 ms |
| free text `&q=a` repeated | 0.48 ms | 0.63 ms | 0.81 ms | 1.52 ms |
| zuey.me URL with about 4000 `q=a` | 1.27 ms | 0.45 ms | 2.50 ms | **36.8 ms** |
| benign 16 KB URL | 0.36 ms | 0.37 ms | 0.34 ms | 0.34 ms |

**Interpretation.**

- The new regex (`RETINA_ASSET_RE`) is anchored and runs only on a domain match of 317 characters or fewer. `isSearchParam` is a `Set` lookup. There is no ReDoS.
- The one outlier, 36.8 ms in node for about 4000 `q` parameters, comes from Node's JS `URLSearchParams.delete`, which splices in a loop. I timed the same operation in Chromium 152 (`new URL(...)`, `searchParams.delete('q')`, `toString()`): 1.7 ms. So browsers stay within budget.
- **Pre-existing, not these PRs (follow-up issue):** a URL with about 3000 distinct sensitive names such as `t1token=…` costs 75 ms in node and 79 ms in Chromium on `main` too. Each `delete` re-serialises the URL. Fix: rebuild the query once from the kept entries instead of calling `delete` per name.
